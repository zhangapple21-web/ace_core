## 一、五个核心问题

### ① 主循环是什么？

```
Question
    ↓
<think> 内部推理
    ↓
判断：信息够不够？
    ├── 不够 → <search>query</search>
    │           ↓
    │       <information>结果</information>
    │           ↓
    │       回到 <think> 继续推理
    │
    └── 够了 → <answer>答案</answer> → 结束
```

**关键特征**：
- 交错式：推理和搜索穿插进行，不是"先搜后推"
- 自驱动：LLM 自己判断什么时候搜、搜什么、什么时候停
- 结构化：用特殊 token（`<think>`/`<search>`/`<information>`/`<answer>`）划分阶段
- 有限轮次：max_turns = 4（论文设置），防止无限循环

**和 ACE 的关系**：
- 类似 ACE 的 Observation → Research → Validator → Governor 循环
- 但 Search-R1 是单模型单循环，ACE 是多角色分工循环
- ACE 的三重交叉验证 = 更强的 "Need More Evidence?" 判断

---

### ② Evidence 怎么流动？

```
搜索结果（原始文档）
    ↓
<information> 封装
    ↓
塞入上下文，成为推理的一部分
    ↓
LLM 自己判断：信哪个？用哪个？要不要再搜？
```

**关键发现**：
- Search-R1 **没有独立的 Evidence Manager**
- 证据管理完全靠 LLM 内部推理（黑箱）
- 只有一个简单的封装：`<information>Doc1: ... Doc2: ...</information>`
- 没有证据评分、没有证据冲突处理、没有证据溯源

**和 ACE 的对比**：

| 维度 | Search-R1 | ACE |
|------|-----------|-----|
| 证据管理 | LLM 黑箱，没有独立层 | 有 Validator 专门做交叉验证 |
| 证据评分 | 无 | 有（经验置信度、来源权重） |
| 冲突处理 | LLM 自己解决 | 三重交叉验证 |
| 溯源 | 无（搜来的就用） | 有（血缘系统、来源追踪） |

**结论**：ACE 在证据管理上已经走得比 Search-R1 远。Search-R1 的证据管理是"模型内隐式"，ACE 是"系统外显式"。

---

### ③ Search Budget 怎么控制？

Search-R1 的预算控制非常简单粗暴：

```
硬限制：max_turns = 4
    ↓
到了 4 轮不管够不够，强制输出答案
```

**没有的东西**：
- ❌ 没有置信度阈值（"90% 就停"）
- ❌ 没有 ROI 判断（"值不值得再搜一次"）
- ❌ 没有连续无提升判定（"搜了三轮没进步就放弃"）
- ❌ 没有动态预算（"难的问题多搜，简单的少搜"）

**为什么这么简单？**
- 因为这是 RL 训练框架，预算是训练时的超参数
- 模型通过奖励函数自己学会"什么时候该停"
- 简单的硬限制反而让训练更稳定

**和 ACE 的关系**：
- ACE 现在也没有显式的 Budget 控制（Research/Validator/Governor 各跑一轮就完了）
- Search-R1 的"max_turns 硬限制"可以借鉴，但太粗糙
- ACE 可以做的更精细：证据置信度 + 边际收益递减判断

---

### ④ Reflection 在哪里发生？

Search-R1 **没有独立的 Reflection 步骤**。

反思完全发生在 `<think>` 标签内部，是推理过程的一部分：

```
<think>
  第一轮：我需要找 A
  → 搜索 A 的结果
  第二轮：A 告诉我需要找 B
  → 搜索 B 的结果
  第三轮：B 的结果和 A 矛盾，我需要验证 C
  → 搜索 C 的结果
  第四轮：现在信息够了，可以回答了
</think>
```

**本质**：Reflection = 持续的推理过程，不是独立步骤

**和 ACE 的对比**：

| 维度 | Search-R1 | ACE |
|------|-----------|-----|
| Reflection 位置 | 内隐在推理中 | 外显为 Validator + Governor |
| 反思角色 | 同一个模型 | 不同角色（Researcher 提，Validator 审，Governor 定） |
| 反思深度 | 受限于单模型上下文 | 多角色多角度 |
| 可观察性 | 黑箱（只能看 `<think>` 输出） | 白箱（每个角色的判断都有记录） |

**结论**：ACE 的 Teacher/Student/Governor 模式是 Reflection 的升级版，从"自己想"变成"多人审"。

### ⑤ Runtime vs Civilization 分界

```
┌───────────────────────────────────────────────────────────┐
│                     RUNTIME（运行时）                      │
│  ┌─────────────────────────────────────────────────────┐  │
│  │  推理循环（<think> → <search> → <information>）     │  │
│  │  搜索引擎调用                                        │  │
│  │  max_turns 预算控制                                  │  │
│  │  特殊 token 解析                                     │  │
│  └─────────────────────────────────────────────────────┘  │
│                                                           │
│  这些都是"身体"：可替换、可训练、可优化                   │
│  换个模型、换个搜索引擎、换个预算，都能跑                 │
└───────────────────────────────────────────────────────────┘

┌───────────────────────────────────────────────────────────┐
│                   CIVILIZATION（文明层）                   │
│                                                           │
│  Search-R1 几乎没有文明层资产                             │
│                                                           │
│  ❌ 没有约束协议（全靠 RL 奖励学出来的）                  │
│  ❌ 没有记忆沉淀（跑完就忘，不积累）                      │
│  ❌ 没有词汇体系（概念不沉淀）                            │
│  ❌ 没有路由系统（只会搜，不会派单）                      │
│  ❌ 没有考古能力（不研究自己的历史）                      │
│                                                           │
│  它是一个"执行器"，不是"文明体"                          │
└───────────────────────────────────────────────────────────┘
```

**关键判断**：
- Search-R1 的全部价值都在 Runtime 层
- 它是一个非常优秀的"搜索执行器"设计
- 但它没有 Civilization 层的任何东西
- 所以 ACE 不需要学 Search-R1 的"怎么做"，只需要吸收它的"循环骨架"

## 三、数据流

```
Search-R1 数据流
================

Question
  │
  ├─→ <think> 推理
  │     │
  │     ├─ 生成 <search>query</search>
  │     │     │
  │     │     └─→ 搜索引擎 API
  │     │           │
  │     │           └─→ <information>结果</information>
  │     │                 │
  │     │                 └─→ 塞回上下文
  │     │                       │
  │     └───────────────────────┘  （继续循环）
  │
  └─→ <answer>答案</answer>
        │
        └─→ 结束
```

**数据特征**：
- 单向流动：问题 → 推理 → 搜索 → 更多推理 → 答案
- 没有持久化：跑完就没了，不积累任何东西
- 没有结构化：证据就是纯文本，靠模型自己理解

## 四、生命周期

```
Search-R1 生命周期
==================

  初始化
    │
    ▼
  第 0 轮：拿到问题，初始推理
    │
    ▼
  第 1 轮：第一次搜索 + 推理
    │
    ▼
  第 2 轮：第二次搜索 + 推理
    │
    ▼
  第 3 轮：第三次搜索 + 推理
    │
    ▼
  第 4 轮：第四次搜索 + 推理 （max_turns 硬限制）
    │
    ▼
  强制输出答案
    │
    ▼
  结束（什么都不留下）
```

**生命周期特点**：
- 线性的，一次性的
- 没有"学习"和"积累"
- 没有"休眠"和"唤醒"
- 没有"演化"和"变异"
- 每一次问答都是独立的

## 五、Runtime / Civilization 分界图

```
┌─────────────────────────────────────────────────────────────┐
│                        RUNTIME                              │
│                                                             │

│                                                             │
├─────────────────────────────────────────────────────────────┤
│                      CIVILIZATION                           │
│                                                             │
│  证据管理协议        ←  ACE 已有（三重交叉验证）             │
│  记忆沉淀机制        ←  ACE 已有（词库/经验/血缘）           │
```

**分界判断**：

- ACE 的核心资产都在 Civilization 层
- 两者重叠很少，互补性很强
- ACE 可以从 Search-R1 吸收的是"循环骨架"，不是"具体实现"

## 六、真正可进入 ACE 文明的骨架（≤5 个）

经过筛选，**只留下 3 个**真正有价值的骨架：

### 骨架 1：交错式证据循环

```
Observation → 推理 → 找证据 → 验证 → 不够 → 再找 → 够了 → 决策
```

**为什么值得进文明**：
- 这不是"搜一次就完"的 RAG 模式
- 是"边想边找，找了再想"的闭环模式
- ACE 现在有 Research/Validator/Governor，但没有"不够就再来一轮"的循环
- 这个骨架可以直接补到 ACE 的治理流程里

**对应 ACE 的改动**：
- Governor 判断"证据够不够"
- 不够的话，把任务打回 Researcher 再找
- 有预算限制（最多几轮、边际收益递减就停）

---

### 骨架 2：证据置信度预算

```
Evidence < 70%  → 继续找
Evidence > 90%  → 停止
连续 3 轮无提升  → 放弃
```

**为什么值得进文明**：
- ACE 现在没有显式的"证据够不够"判断标准
- 全靠 Governor 凭感觉（其实是 prompt）决定
- 有了置信度阈值，治理决策就有了量化依据
- ROI 原则（值不值得）有了落地的地方

**对应 ACE 的改动**：
- Validator 输出证据置信度分数
- Governor 根据置信度决定是否继续
- 连续无提升自动终止（避免浪费算力）

---

### 骨架 3：证据封装协议

```
原始证据 → 标准化封装 → 进入证据池 → 可追溯、可评分、可对比
```

**为什么值得进文明**：
- Search-R1 的 `<information>` 封装很粗糙，但思路是对的
- 证据不应该是一堆散乱的文本
- 应该是结构化的：来源、置信度、时间、相关概念
- ACE 有血缘系统，但证据层面的结构化还不够

**对应 ACE 的改动**：
- 定义 Evidence 数据结构（来源、置信度、时间、关联概念）
- 所有 Researcher 产出的证据都按这个结构封装
- Validator 基于结构化证据做交叉验证

---

### 不进文明的（为什么不收）

| 东西 | 为什么不收 |
|------|-----------|
| RL 训练框架 | ACE 不是训练系统，是运行系统 |
| 特殊 token 协议 | ACE 用角色分工替代，更灵活 |
| 搜索引擎接口 | ACE 已经有 web_scout，不需要再抄 |
| `<think>` 推理模式 | 单模型内隐推理，不如 ACE 的多角色外显推理 |
| 奖励设计 | RL 奖励 = 训练用，ACE 不需要 |

---

## 七、结论

Search-R1 是一个**优秀的搜索执行器设计**，但不是一个文明系统。

它的价值在于：
- 证明了"交错式搜索 + 推理"比"一次性 RAG"强很多
- 证明了简单的预算控制（max_turns）足够有效
- 证明了证据封装（`<information>`）能让模型更清晰地处理外部信息

ACE 不需要抄 Search-R1 的任何代码。

只需要吸收三个骨架：
1. **交错式证据循环** — 补全"不够就再来一轮"的闭环
2. **证据置信度预算** — 给治理决策一个量化的停止标准
3. **证据封装协议** — 让证据结构化、可追溯、可对比

这三个骨架都落在 Civilization 层，不是 Runtime 层。
它们增强的是 ACE 的治理协议，不是 ACE 的工具能力。
